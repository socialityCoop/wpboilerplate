# Bedrock boilerplate installation

Use this workflow only when installing a new site from this Roots Bedrock boilerplate. The user has WAMP and WP-CLI. Follow the steps in order and do not skip the constraints.

## 1. Apache virtual host

- Set the virtual-host name to the current project folder name.
- Set the document root to this project's `web/` folder only. Do not inspect other folders to choose a document root.
- Use the latest PHP version present in the WAMP installation through FCGI.
- Typical files are `C:\wamp64\bin\apache\apache*\conf\extra\httpd-vhosts.conf` and the WAMP PHP FCGI configuration.
- The vhost should use `ServerName {folder}.local` (or the folder name as-is when it already includes `.local`), with `DocumentRoot` and `<Directory>` pointing to `{project}\web`.
- Ask the user to reload Apache. Do not reload it yourself, and continue without waiting for confirmation.

## 2. Windows hosts file

- Ask the user to add the vhost hostname to `C:\Windows\System32\drivers\etc\hosts`, for example `127.0.0.1 {hostname}`.
- Never read, write, or open the hosts file yourself.
- Continue without waiting for confirmation.

## 3. Composer packages

- In `composer.json`, update theme and plugin requirements (`wp-theme/*` and `wp-plugin/*`) to the latest versions listed on [WP Packages](https://wp-packages.org/), using the existing `https://repo.wp-packages.org` repository.
- Leave PHP, Bedrock, and Roots core constraints unchanged unless they block installation.
- Run `composer install`, then `composer update`.

## 4. Database and `.env`

- Create a new MySQL database and user for this site in WAMP MySQL. Use the same value for the database name and username.
- Use a strong password that does not contain the database name or the current year.
- Do not test or verify database connectivity afterward.
- Copy `.env.example` to `.env` and fill in the database name, username, and password.
- Fetch WordPress salts from [roots.io/salts.html](https://roots.io/salts.html) and add them to `.env`.
- Set `WP_HOME` to the local URL whose hostname matches the folder/vhost. Set `WP_SITEURL` to `${WP_HOME}/wp` when that matches the example file's structure.

## 5. WordPress installation with WP-CLI

- WordPress is already installed as a Composer package in `web/wp`.
- Do not check whether WordPress is already installed.
- Use `wp core install` with the project path and the required site settings.
- Use English (`en_US`) as the language.
- Ask the user for the site title; never invent one.
- Use `sociality` as the administrator username and `contact@sociality.gr` as the administrator email.
- Use the password generated by WordPress/WP-CLI. Print that generated password in the chat; do not invent a replacement password.
- Discourage search engines (`blog_public = 0`).
- Set the timezone to `Athens` and the permalink structure to `post-name`.

## 6. Child theme and plugins

- Run `npm install` in `web/app/themes/understrap-child`.
- Activate the `understrap-child` template in WordPress.
- Change the `Text Domain` in its `style.css` to match the project.
- Rename `web/app/plugins/site-specific-plugin` to match the project and activate it. Change its `Text Domain` to match the project.
- Activate `disable-gutenberg`, `mcp-adapter`, and `enable-abilities-for-mcp`.
- Configure the WordPress MCP server in Zed through **Settings → AI → MCP Servers**. Zed stores this under `context_servers`; do not update `.cursor/mcp.json` for Zed. If Cursor compatibility is still needed, its existing `.cursor/mcp.json` can be maintained separately.

## Constraints

- Do not alter boilerplate files except `composer.json`, `composer.lock`, and `.env` during installation.
- Use the WordPress MCP server and WP-CLI when possible.
- Do not proceed to theme or content work unless the user explicitly asks. This skill is installation-only.
